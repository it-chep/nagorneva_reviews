# nagorneva_reviews

Сервис отзывов докторов на Go. Сборка приложения находится в `internal/app.go` и `internal/init.go`, транспорт — в `internal/app/server`.

HTTP JSON → grpc-gateway / Clay descriptor → interceptor → API → action → DAL → PostgreSQL.

Нативный gRPC → Clay gRPC-сервер → interceptor → тот же API.

Как в `medblogers_base`, Clay регистрирует нативный gRPC и HTTP grpc-gateway по сгенерированным service descriptors. Gateway вызывает сервис внутри процесса; отдельное сетевое gRPC-соединение между HTTP и обработчиками не требуется. Прямые gRPC-запросы и JSON-запросы проходят одну проверку JWT через `WithGRPCUnaryMiddlewares`. Multipart-загрузка фото остаётся отдельным HTTP-адаптером с проверкой того же токена.

## Архитектура

```text
internal/
  app/api/                       # Преобразование protobuf ↔ DTO
  app/server/                    # HTTP, grpc-gateway, gRPC и shutdown
  app/middleware/                # JWT и CORS
  config/                        # Конфигурация из окружения
  modules/
    admin/
      module.go                  # Сборка зависимостей
      action/login/              # Вход и отдельный DAL
      client/s3/                 # Внешнее хранилище
      entities/
        aggregator.go
        doctors/                 # Аналогично: users, cities, specialties, courses, reviews
          aggregator.go
          action/create_doctor/  # Сценарий и небольшой интерфейс Storage
          action/update_doctor/
          action/upload_doctor_photo/
          dto/                   # Типизированные входы и результаты
          dal/                   # SQL конкретной сущности
        users/service/password/  # Проверка и хеширование пароля
    reviews/
      action/<operation>/        # Публичный сценарий
        dal/                     # Его SQL
      domain/                    # Модели публичного каталога
  pkg/postgres/                  # Интерфейс DB, чтение строк, перевод ошибок БД
  pkg/domain_error/              # Ошибки, не зависящие от PostgreSQL и транспорта
```

Actions не импортируют pgx и не строят SQL. Общего CRUD с именами таблиц и `map[string]any` нет: каждая сущность имеет собственный репозиторий. Пакет `dto` задаёт контракт с actions и API; PostgreSQL-типы остаются в DAL. Интерфейсы зависимостей определены рядом с actions. Слой `service` используется для самостоятельной бизнес-логики, а простые операции вызывают DAL напрямую.

Необязательные поля PATCH представлены указателями: отсутствие поля сохраняет значение, а `false`, `0` и пустая строка применяются явно. Создание и обновление врача вместе с чтением связанных справочников выполняются одним SQL-выражением. Репозитории принимают `postgres.DB`, который реализуют и пул, и транзакция pgx; отдельный механизм транзакций пока не требуется.

Создание начального администратора вынесено в `users/action/ensure_initial_user`. Повторный запуск не меняет существующий пароль, а конкурентная вставка защищена `ON CONFLICT`. Существующие ограничения и внешние ключи БД сохранены.

## Модули

- `reviews` — публичные методы карты и фильтра отзывов без авторизации.
- `admin` — CRUD сущностей, просмотр отзывов врача, загрузка фото и JWT-вход. Все методы `/api/v1/admin/*`, кроме `/login`, требуют `Authorization: Bearer <access_token>`.

`personal_data_consent` не удаляет фактические данные врача из БД. Он управляет их выдачей в публичном `GetDoctorsOnMap`: без согласия API возвращает пустые `full_name` и `photo`.

## Быстрый старт

```bash
cp .env.example .env
docker compose up -d
make migrate-up
go run ./cmd/nagorneva_reviews
```

Перед первым запуском задайте `JWT_SECRET` длиной не менее 32 символов. При указании `ADMIN_EMAIL` и `ADMIN_PASSWORD` приложение создаст администратора с этим email при запуске, если его ещё нет — пароль сохраняется только в bcrypt-хеше.

HTTP API работает через grpc-gateway на `HTTP_ADDR` (по умолчанию `:8080`), а нативный gRPC API — на `GRPC_ADDR` (по умолчанию `:7002`). Оба транспорта используют контракты из `api/`.

`DEBUG=false` по умолчанию. При `DEBUG=true` JWT-проверка отключается для admin HTTP и native gRPC вызовов — используйте это только локально.

Для браузерных запросов задайте `CORS_ALLOWED_ORIGINS` как список точных origin через запятую, например `https://reviews.example.ru,https://admin.example.ru`. По умолчанию разрешены только `http://localhost:3000` и `http://localhost:5173`; значения с путём, query-параметрами или фрагментом игнорируются.

## API

Контракты находятся в `api/reviews/reviews.proto` и `api/admin/admin.proto`. Для генерации Go-сообщений, gRPC-клиентов/сервера, gateway и OpenAPI:

```bash
make buf
```

Версии плагинов зафиксированы в `buf.gen.yaml`, зависимости proto — в `buf.lock`. Команда не обновляет их автоматически. Go-код, OpenAPI и Clay descriptors (`*.pb.goclay.go`) генерируются в `gen/go`. Для локального плагина `protoc-gen-goclay` выполните `make deps`. Clay объединяет OpenAPI-схемы сервисов при запуске.

Swagger UI доступен по `/docs`, объединённая схема — по `/swagger.json`. Имена RPC и существующие HTTP URL сохранены. JSON gateway использует стандартный protobuf-формат: camelCase в ответах, `int64` как строки; во входных запросах допустимы также имена полей из proto в snake_case.

Ошибки отсутствующей записи преобразуются в gRPC `NotFound` / HTTP 404, дубликата — в `AlreadyExists` / 409, внешнего ключа — в `FailedPrecondition` / 400, ограничений данных — в `InvalidArgument` / 400. Внутренние ошибки не раскрывают SQL клиенту.

Основные HTTP методы:

| Метод | Назначение |
|---|---|
| `POST /api/v1/doctors_on_map` | Доктора по координатам, с городом, доступным фото и активными отзывами/курсами |
| `POST /api/v1/doctors/filter` | Фильтр врачей по `city_ids`, `specialty_ids`, `course_ids`, `is_active`, `personal_data_consent`, `reviews_sort` |
| `POST /api/v1/reviews/filter` | Фильтр отзывов по `course_id`, `lat`, `lon`, `radius_km` |
| `POST /api/v1/admin/login` | Вход администратора |
| `/api/v1/admin/{users,cities,specialties,doctors,courses,reviews}` | `GET`, `POST`, `GET/{id}`, `PATCH/{id}`, `DELETE/{id}` |
| `POST /api/v1/admin/doctors/filter` | Фильтр врачей для админки, включая неактивных и врачей с `city_id = 2` |
| `GET /api/v1/admin/doctors/{id}/courses` | Пройденные курсы выбранного врача |
| `POST /api/v1/admin/doctors/{id}/courses` | Добавить связь с курсом, тело `{ "course_id": 1 }` |
| `DELETE /api/v1/admin/doctors/{id}/courses/{course_id}` | Удалить только связь врача с курсом |
| `GET /api/v1/admin/doctors/{id}/reviews` | Все отзывы выбранного врача, включая неактивные |
| `POST /api/v1/admin/doctors/{id}/photo` | `multipart/form-data` с полем `photo` либо JSON protobuf с фото в base64; загрузка в S3 |

В `/api/v1/doctors_on_map` сначала возвращаются врачи с активными отзывами, затем без них; внутри групп порядок по ID. Каждый врач содержит `courses`: список объектов с `id`, `name` и `siteLink`. Курсы берутся из связи `doctor_courses`, включая курсы без отзывов; отсутствие ссылки допускается.

Ответ `/api/v1/doctors_on_map` также содержит `all_doctors_count`: общее число активных врачей с `city_id != 2`, независимо от координат и радиуса запроса. Имя этого поля в JSON сохранено в snake_case; значение `int64` передаётся строкой, включая `"0"` при пустом каталоге. Для полной карты используется существующий кэш на 60 секунд.

Админские методы курсов требуют авторизации. GET возвращает `{ "courses": [...] }`, POST и DELETE — `{}`. Повторный POST не создаёт дубликат. Удаление связи не удаляет сам курс или отзывы врача. Несуществующие врач/курс при добавлении и отсутствующая связь при удалении возвращают 404; неположительные ID — 400.

Публичные отзывы в `/api/v1/reviews/filter` и `/api/v1/doctors_on_map` содержат ссылку на сайт курса: `courseSiteLink` в JSON (`course_site_link` в protobuf). Значение берётся из `site_link` курса, заданного через административный API. Если ссылка не задана, строковое значение пустое; JSON-сериализатор может опустить такое поле.

Загрузка фотографий временно отключена: в `.env` и `.env.example` оставьте `S3_BUCKET=` пустым. В этом режиме S3-клиент не создаётся, ключи хранилища не требуются, а multipart-загрузка фото возвращает HTTP 503 (gRPC — `FailedPrecondition`). Остальные функции приложения работают без S3.

Чтобы вернуть загрузку фотографий через Yandex Object Storage по схеме из `medblogers_base`, укажите существующий бакет и его статические ключи в `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и `S3_BUCKET`. Приложение не создаёт бакет само. `S3_PUBLIC_URL` необязателен: по умолчанию ссылки имеют вид `https://storage.yandexcloud.net/<S3_BUCKET>/<object-key>`. Имя объекта — `images/user_<doctor_id>_<timestamp>.<ext>`.

Для этого проекта выбран отдельный бакет `nagorneva-reviews-photos`. Параметры подключения хранятся в локальном `.env` (не попадает в Git); в `.env.example` бакет и ключи оставлены пустыми. После изменения `.env` перезапустите backend. Если `S3_BUCKET` задан в окружении процесса, очистите его и там: переменные окружения имеют приоритет над `.env`. Для отображения фото на публичной карте бакет должен разрешать анонимный `s3:GetObject` для `images/*`; публичный список объектов и публичная запись не нужны. Без `S3_BUCKET` загрузка отключена, а при указанном бакете без ключей приложение вернёт ошибку при запуске.

При первичной настройке создайте бакет в Yandex Cloud и примените политику из `scripts/s3-public-photos-policy.json`. Сервисному аккаунту, которому принадлежат статические ключи, нужен доступ к загрузке объектов в новый бакет. Если создание через S3 API возвращает `AccessDenied`, используйте аккаунт с правом создания бакетов. Существующие бакеты `medblogers_base` для этого проекта не используются.

## Важное решение по данным

В исходном ТЗ `speciallity` содержит опечатку. В БД и API использовано согласованное имя `specialties` / `specialty_id`. Это предотвращает постоянную неоднозначность в SQL и фронтенде. Координаты врача сохранены отдельно от города: город задаёт фильтр и справочник, а координаты врача — точку на карте.

В `POST /api/v1/doctors/filter` и `POST /api/v1/admin/doctors/filter` значения внутри одного массива работают как «или», а непустые группы фильтров объединяются как «и». Например, врач из любого указанного города, с любой указанной специальностью и прошедший любой указанный курс. Поле `course_ids` сверяется с отдельной связью `doctor_courses`, а не с текстом отзывов. Публичные методы всегда исключают неактивных врачей и врачей без города (`city_id = 2`). В админке эти врачи доступны. Необязательные `is_active` и `personal_data_consent` принимают `true` или `false`; без этих полей админский поиск не ограничивает соответствующие признаки. Админский поиск возвращает фото без публичного маскирования и считает все отзывы, публичный — только активные отзывы. `reviews_sort` принимает `REVIEWS_SORT_DESC` или `REVIEWS_SORT_ASC`; без него и при одинаковом числе отзывов врачи отсортированы по ID. Ответ содержит `doctor_count` — общее число врачей, совпавших с фильтром.


## Подготовка импорта врачей из Excel

`scripts/prepare_doctors_import.py` готовит SQL для `doctors` и `doctor_courses` из листа `students` и существующих CSV-справочников без заголовков. Требуется Python 3.10+ и `openpyxl`. Скрипт не подключается к БД и не создаёт справочники.

```bash
python3 scripts/prepare_doctors_import.py \
  --xlsx /path/to/students.xlsx \
  --cities /path/to/cities.csv \
  --courses /path/to/courses.csv \
  --specialties /path/to/specialties.csv \
  --specialty-id 2 \
  --output-dir outputs/doctors_import_20261026
```

`--specialty-id` — обязательная настройка: в исходном Excel специальностей нет. Значение `2` в предоставленном справочнике означает «Ультразвуковая диагностика». Совпадающие email объединяются с сохранением курсов и номеров исходных строк. Одинаковые имена при разных email автоматически не объединяются. Пустые имена и тестовые записи перечисляются в отчёте, а не добавляются как вымышленные врачи.

Результат: `import_doctors.sql`, подробный `report.json` и читаемый `report.txt`. Для отсутствующих или противоречивых городов используется существующая запись «Не указано», исходные значения сохраняются в отчёте. Все врачи создаются неактивными; `name` и `full_name` сохраняют имя из источника, перед активацией нужно проверить публичное отображение. Фото и отзывы на этом этапе не импортируются. Файлы результата содержат персональные данные и исключены из Git.

Уточнения можно передать через `--overrides /path/to/overrides.json`: объект `cities` сопоставляет исходный текст города с ID, объект `doctors` сопоставляет номер **первой строки Excel в объединённой группе** с полями `full_name`, `name`, `city_id`, `specialty_id`. Номера и варианты исходных значений есть в отчёте.

Запуск подготовленного SQL вручную:

```bash
psql -X --set=ON_ERROR_STOP=1 --file=outputs/doctors_import_20261026/import_doctors.sql "$DATABASE_URL"
```

Вставка выполняется одной транзакцией. SQL проверяет ID и названия используемых справочников. При совпадении исходного ФИО с существующим врачом весь импорт останавливается: в схеме нет email или внешнего ключа источника, поэтому автоматически связывать существующих врачей нельзя. Повторный запуск того же файла останавливается до вставки. Существующие врачи, отзывы и справочники не меняются. При успехе SQL возвращает соответствие номеров строк Excel новым `doctor_id`; сохраните его для последующего импорта отзывов.

## Подготовка импорта отзывов

`scripts/prepare_reviews_import.py` читает отзывы из F:I того же Excel и использует `report.json` предыдущего импорта врачей. Контрольные суммы защищают от случайного смешивания версий Excel и справочника курсов. Результат содержит только вставку отзывов; схема и существующие врачи не изменяются.

```bash
python3 scripts/prepare_reviews_import.py \
  --xlsx /path/to/students.xlsx \
  --doctors-report outputs/doctors_import_20261026/report.json \
  --courses /path/to/courses.csv \
  --rating 5 \
  --overrides outputs/reviews_import_20261026/course_overrides.json \
  --output-dir outputs/reviews_import_20261026
```

Оценка `5` установлена по прямому указанию пользователя; в исходном Excel оценок нет. Все отзывы создаются неактивными, `created_at` означает время импорта. Текст сохраняется полностью. Курс выбирается по явному заголовку, пометке `(отзыв)` или единственному курсу исходной строки. Уточнения после прочтения текста задаются необязательным `--overrides`: ключ — адрес ячейки, значение — `course_id` и `evidence` с основанием выбора. Неоднозначные отзывы и противоречия со списком курсов врача остаются в `report.txt` и `report.json`, без вставки.

Запускайте `import_reviews.sql` **после** импорта врачей:

```bash
psql -X --set=ON_ERROR_STOP=1 --file=outputs/reviews_import_20261026/import_reviews.sql "$DATABASE_URL"
```

SQL требует единственного совпадения врача по ФИО, городу, специальности и точному набору курсов. Если врачей уже редактировали, можно передать генератору `--doctor-ids` с JSON `source_key -> doctor_id`, используя сохранённый результат импорта врачей. Указанный ID проверяется по ФИО и наличию курса. Отсутствующие или неоднозначные совпадения отменяют всю транзакцию. Повторный запуск пропускает одинаковые тексты того же врача по тому же курсу, не меняя существующие отзывы.

## Восстановление городов после импорта

`scripts/prepare_city_recovery.py` готовит отдельный SQL из исходного отчёта врачей и проверенных координат в `scripts/data/city_recovery_places_20261031.json` (GeoNames, CC BY 4.0). Генератор работает локально, без подключения к БД и без передачи данных врачей геосервисам.

```bash
python3 scripts/prepare_city_recovery.py \
  --doctors-report outputs/doctors_import_20261026/report.json \
  --cities /path/to/cities.csv \
  --output-dir outputs/city_recovery_20261031
```

По указанию пользователя записи только со страной привязываются к столице: Казахстан → Астана, Россия → Москва, Беларусь → Минск, Сербия → Белград. Это условная привязка к центру столицы, а не подтверждение проживания в ней. Страна вместе с конкретным городом сохраняет именно этот город. Пустые ответы, неоднозначные населённые пункты, регионы без города и противоречивые города одного контакта остаются в отчёте без обновления.

В подготовленном пакете 109 врачей и 84 места назначения, включая семь замен страны столицей. Из исходных 62 городов повторно используются Москва и Астана; остальные 82 добавляются, если их ещё нет в БД. Существующие варианты названий учитываются при близких координатах. ID новых городов выделяются БД; последовательность при необходимости продвигается за существующие ID, без перемотки назад.

Запускайте SQL **после первоначального импорта врачей и отзывов**:

```bash
psql -X --set=ON_ERROR_STOP=1 --file=outputs/city_recovery_20261031/restore_cities.sql "$DATABASE_URL"
```

SQL обновляет `city_id`, `lat`, `lon`, `updated_at` только у врачей с городом «Не указано». Координаты берутся из конечной записи города. Активность и остальные данные не меняются. Врачи сопоставляются по ФИО, специальности и точному набору курсов; если специальность или набор курсов изменились, передайте `--doctor-ids` с проверенным JSON `source_key -> doctor_id`. Указанный ID проверяется по исходному ФИО; изменённые ФИО требуют отдельной сверки сопоставления. При отсутствии или неоднозначности сопоставления транзакция прерывается целиком. Уже исправленные вручную города сохраняются. Повторный запуск ничего не меняет.

Сохраните результат SQL с `source_key`, `doctor_id`, предыдущими координатами и статусом обновления. При последующем запуске старого импорта отзывов используйте его `--doctor-ids`: исходный отчёт врачей намеренно не переписывается, а прежняя проверка врача включает старый город.

## Проверки

```bash
make build
make test-race
make lint
TEST_DATABASE_URL='postgres://reviews_test:test@localhost:55493/reviews_test?sslmode=disable' make test-integration
```

`make deps` устанавливает Buf, Goose, protoc-gen-goclay и golangci-lint v2 в `bin/`. Интеграционные тесты требуют отдельную тестовую PostgreSQL: создают временную схему, применяют миграции и удаляют только эту схему после выполнения. Отсутствие `TEST_DATABASE_URL` считается ошибкой запуска интеграционных тестов.

Для локальной тестовой БД:

```bash
docker run --rm -d --name reviews-test-db \
  -p 127.0.0.1:55493:5432 \
  -e POSTGRES_USER=reviews_test -e POSTGRES_PASSWORD=test \
  -e POSTGRES_DB=reviews_test postgres:15
# После тестов:
docker stop reviews-test-db
```

CI выполняет сборку, тесты с детектором гонок, интеграционные тесты PostgreSQL и линтер. Транспортные тесты поднимают HTTP и gRPC на случайных локальных портах и проверяют авторизацию обоих транспортов, CORS, JSON/multipart-маршруты и большие фото. Интеграционные тесты проверяют типизированный CRUD, частичные обновления, связи и ограничения БД, публичные фильтры и скрытие персональных данных.
